20:15  13.32      ← เริ่มดิ่ง
20:30  12.76
20:45  12.45

**แต่แผนบอกแค่จุดเดียว — จริง ๆ เกิดทั้งสาย:** ตรวจ max drop ต่อชั่วโมงได้ จุด 16 = 0.56 ม. ·

## 2. สิ่งที่แผนพูดเกินจริง / ผิด — ต้องแก้ก่อนใช้

### 2.1 ⚠️ ตาราง Δ ใช้ "น้ำสูงสุด − ต่ำสุด" ซึ่งปนสัญญาณปฏิบัติการเข้าไป (สำคัญสุด)

แผนรายงาน Δ ของคลองสายใหญ่ = **0.99–1.50 ม.** และระบุ "น้ำสูงสุด 26 ก.ย. 16:00–22:00"
แต่เมื่อคำนวณเทียบ **ระดับก่อนเหตุการณ์ (baseline 25 ก.ย.)** แทน "ต่ำสุด":

| จุด | baseline (25 ก.ย.) | น้ำสูงสุด | Δ แบบแผน (น้ำสูงสุด−ต่ำสุด) | **Δ จริง (น้ำสูงสุด−baseline)** | max 15-min step |
|---|---:|---:|---:|---:|---:|
| 16 กม.0+970 | 13.84 | 13.89 | 1.50 | **+0.05** | 0.56 |
| 17 กม.1+830 | 13.41 | 13.57 | 1.15 | +0.16 | 0.39 |
| 18 กม.4+896 | 12.61 | 13.53 | 0.99 | +0.92 | 0.03 |
| 19 กม.6+745 | 13.05 | 14.01 | 1.45 | +0.96 | 0.41 |
| 20 กม.8+550 | 13.02 | 13.83 | 1.07 | +0.81 | 0.32 |
| 21 กม.11+740 | 13.13 | 14.50 | 1.41 | +1.37 | 0.47 |

> ⚠️ **หน่วยของคอลัมน์สุดท้าย:** ตัวเลข 0.56/0.39/0.32
> คือ **การดิ่งมากสุดใน 1 ช่วง 15 นาที** ไม่ใช่ต่อชั่วโมง (ตรวจซ้ำกับ `data/20_multistation_levels/`)
> **ค่าต่อชั่วโมงจริง** (จาก `analysis/all_stations_network.md` ซึ่งเป็นทางการ): 16 = **1.39** · 17 = 0.71 ·
> 18 = 0.09 · 19 = 0.98 · 20 = 0.61 · 21 = 0.87 ม./ชม.
> → ข้อสรุป **ไม่เปลี่ยน** (ขั้นปฏิบัติการใหญ่กว่าการขึ้นเชิงอุทกวิทยามาก: จุด 16 = 27.8 เท่า) แต่ตัวเลขต้องใช้ของ P1


**ปัญหา:** จุด 16 "ต่ำสุด" เกิด **หลัง** การปิดบาน ไม่ใช่ก่อน → Δ 1.50 ม. เป็น **การปิดบาน 97%** ไม่ใช่การตอบสนองต่อฝน
→ ถ้าใส่ตารางนี้ในรายงาน จะได้ตัวเลขที่ดูเป็นฟิสิกส์ แต่ถูก artifact ครอบงำ

**วิธีแก้:** แยกเป็น 2 คอลัมน์ — "การขึ้นเชิงอุทกวิทยา (น้ำสูงสุด−baseline)" กับ "ขั้นปฏิบัติการ (max drop/ชม.)"
ผลพลอยได้: พอแยกแล้ว เรื่องสวิตช์จะชัดขึ้น ไม่ต้องพึ่งตัวเลขที่กำกวม

### 2.2 ❌ "19 จุด มีระดับ+Q+ฝน" — ผิด

ตรวจสดทีละจุด (คอลัมน์ที่ 3/4 = Q, ฝน):

| กลุ่ม | จุด | มีอะไร |
|---|---|---|
| คลองสายใหญ่ | 16, 17, 18, 19, 20, 21 | **ระดับเท่านั้น** (Q = `-`, ฝน = `-`) |
| NY.4 สมอปูน | 23 | ระดับ (+Q = 0.000 = ใช้ไม่ได้) |
| ปตร./สาขา | 26, 28, 30, 84 | ระดับ + Q |
| แม่น้ำหลัก | 61, 62, 63 | ระดับ + Q |
| คลอง กม.14+118 | 72 | ระดับ + Q |

→ **คลอง 6 จุดไม่มี Q** ✓ (ยืนยันแล้ว) — แต่ **"ฝนไม่มีเลย" ผิด**
→ การสรุปจาก **แถวเดียวต่อสถานี** อ่อนเกินไป · ตรวจทั้งเดือน (`analysis/all_stations_network.md`):
  **มีฝนจริงที่ 61 (11.2%) · 62 (10.3%) · 63 (11.3%) · 84 (0.2%)** · จุดคลอง 16–21 และ 72 ไม่มีฝน
→ ผลต่อแผน: ข้อเสนอ "วิเคราะห์ปริมาณส่งน้ำคลองจากการเปลี่ยนระดับ" ต้องมี **rating curve คลอง** ก่อน (แผนยอมรับใน "งานต่อ" #3 แต่ข้อความหลักเขียนเหมือนทำได้แล้ว)
→ จุด 30 มีค่า **Q = −4.990** (ค่าลบ) = ต้องตรวจคุณภาพข้อมูลรายจุด ✓ (ยืนยันแล้ว — และพบเพิ่มว่าเป็น sentinel ตอน re-datum)

### 2.3 ⚠️ "NY.3 บ้านนา" — ข้อมูลไม่แน่นอน (intermittent)

ตัวเลข "จริงคือ **485 แถว** ... step 5.83 ม./ชม." **ไม่มี artifact ใดใน repo หนุน — ห้ามใช้**

**สิ่งที่ตรวจได้จริง (และสับสน):**
- ดึงสด **1–30 ก.ย. 69** ด้วยสคริปต์ `fetch_multistation_levels.py` → **0 แถว** (ทดสอบซ้ำ 3 ครั้ง ทุกหน้าต่างเวลา)
- แต่ **การดึงช่วงหนึ่งของวันเดียวกัน** ได้ **2,785 แถว** (ค่า 0–6.51 ม. median 4.15 — ดูเหมือนซีรีส์จริง)
- `khundan_new_stations_event_check.json` ของ AI อีกตัว ก็ได้ **0 แถว**

→ **สรุปที่ปลอดภัย: n_id=105 (NY.3) "ไม่แน่นอน" (intermittent)** — **ห้ามสรุปทั้ง "มีข้อมูล" และ "ไม่มีข้อมูล" แบบตายตัว**
→ ต้นทางเป็น **ข้อมูลสดที่เปลี่ยนได้** → ต้องดึงซ้ำก่อนใช้ทุกครั้ง (บันทึกไว้ใน `data/20_multistation_levels/manifest.md`)
→ ข้อสรุปของแผนที่ว่า "NY.3 = 0 แถว / ออฟไลน์" **ไม่ผิด** ในเชิงปฏิบัติ — แต่คำอธิบายที่ถูกคือ "ไม่แน่นอน" ไม่ใช่ "หาย"


### 2.4 ⚠️ "ตรวจ M4 ได้จากข้อมูลจริง" — ติดป้ายผิด
การที่เขื่อน **งดส่งน้ำเข้าคลอง** ช่วงน้ำสูงสุดเมือง = กลไกแบบ **M3** (หยุดปล่อยผ่านหน้าต่างน้ำสูงสุด) ไม่ใช่ **M4** (เบี่ยงน้ำออกปลายน้ำก่อนช่วงน้ำสูงสุด)
→ ที่จริงข้อค้นพบนี้ **หนุน M3** และ **หนุนเป้าหมาย 2** ("ผู้ปฏิบัติมีแนวคิดหน้าต่างน้ำสูงสุดอยู่แล้ว") — ควรติดป้ายให้ตรง จะทรงพลังกว่า

### 2.5 ⚠️ thaiwater ต้องกรอง `station_type` ก่อนใช้
ทะเบียนจริง (11,483 สถานี · ในนครนายก 66 สถานี) มีรหัสที่แผนอ้างครบ: NYK000, NYK001–013, 417002–417004, TNy9–TNy12, NY3 ✓
**แต่ `station_type` ปนกัน:** `W` = ระดับน้ำ · `R` = ฝน · `A` = อื่น ๆ
เช่น `NYK000 องครักษ์` = type **A**, `NYK001` = **A**, `417002 บ้านนา` = **R**
→ ถ้าดึงตามรหัสโดยไม่กรอง type จะได้ **ฝน** แทน **ระดับน้ำ** · และสถานีระดับน้ำจริงมักเป็นรหัส `ridhydro_*` (เช่น `ridhydro_TNy10` type W qmax 70, `ridhydro_TNy9` type W qmax 254)

### 2.6 ⚠️ "โมเดลเส้นทาง 4 จุด" = ของใหม่ ไม่ใช่การขยาย
โครงการปัจจุบันเป็น **lumped lag ค่าเดียว ไม่มี routing** การทำโมเดลหลายจุดต่อเนื่องต้องมี **routing scheme** (เช่น Muskingum) + สอบเทียบ — เป็น **การพัฒนาใหม่** ไม่ใช่ "สคริปต์เดิม ขยาย STATIONS"
→ อย่าประเมินงานต่ำเกิน (แผนเขียนเหมือนเป็นงานต่อยอดเล็ก)

## 3. ช่องว่างที่สำคัญที่สุด: Reproducibility

สิ่งที่เก็บไว้มีแค่ **สรุป** (`all_stations_event_summary.json`, `khundan_new_stations_event_check.json`) — **ไม่มี raw series และไม่มีสคริปต์ดึง**

→ ข้อค้นพบหลัก (สวิตช์คลอง) **พิสูจน์จาก repo ไม่ได้** — ต้องดึงสดซ้ำจึงยืนยันได้
→ ขัดกับ protocol ของโครงการเอง (raw-first + `manifest.md` + SHA-256) และขัดกับแบบแผนเดิมที่ `fetch_khundan_training.py` เซฟลง `data/16_training_data/` พร้อม `_hashes.txt`

**ต้องทำก่อนสร้างอะไรทับ:** เขียนสคริปต์ดึง + เซฟ raw ลง `data/` + manifest + hash

## 4. ความลึกข้อมูล 15 นาที — ย้อนได้ถึง 5 ปี

docstring ของ `analysis/fetch_khundan_training.py` ระบุรูปแบบการดึงไว้ถูกต้องแล้ว แต่ระวังการตีความ API แบบลวก ๆ ว่า
> "ช่วง <=7 วัน -> ราย 15 นาที / ยาวกว่านั้น -> รายวัน 07:00"

**ไม่จริง** — ทดสอบแล้ว 15 นาทีใช้ได้ถึง 5 ปี (138,822 แถว) · ไฟล์ `*FULLYEAR*.csv` ของโครงการเองก็เป็น 15 นาที
→ ถ้าเข้าใจผิดว่า "ดึง 5 ปี 15 นาทีไม่ได้" จะยึดเงื่อนไขตั้งต้นของแผนนี้ผิดตั้งแต่ต้น

## 5. คำตอบตรงคำถาม: "เหมือนเดิมหรือต่างจากเดิม"

### เหมือนเดิม (ไม่ต้องแก้)
- rating curve · datum · BANKFULL · เกณฑ์ URC/LRC — ยังเป็นแกนเดิม
- **วิธี** attribution (12%:88%) — ยังเป็น water balance ที่ Ny.7 การเพิ่มจุดไม่เปลี่ยนวิธี แค่เพิ่มที่ *ตรวจทาน*
- โครง 4 วัตถุประสงค์เดิม ไม่ต้องเพิ่มวัตถุประสงค์ใหม่
- Ny.7 ยังเป็นสมอ — จุดอื่นเป็น *บริบท* ไม่ใช่ตัวแทน

### ต่างจริง (ได้ของใหม่)
- **เป้าหมาย 1**: ได้บันทึกปฏิบัติการชุดที่สอง (บานคลอง) **โดยไม่ต้องรอ FOI** — ยืนยันแล้วว่าจริง
- **เป้าหมาย 3**: อธิบาย "ทำไมองครักษ์น้ำขังนานสุด" ด้วยจุดวัดจริง (lag 23 ชม.) ไม่ใช่แค่ภาพถ่าย
- **เป้าหมาย 2**: ตอบได้ **"ทิศทาง"** (เปิด/ปิดบานเมื่อไร) แต่ **ยังตอบ "ปริมาณ" ไม่ได้** (ติด rating คลอง)

### เปลี่ยนแนว (งานใหม่ ไม่ใช่การขยาย)
- **เป้าหมาย 4**: จาก "จุด" → "เครือข่าย" = ต้องมี routing = งานใหม่

## 6. ข้อเสนอปรับแผน (เรียงลำดับ)

1. **เซฟ raw + สคริปต์ + manifest ก่อน** (protocol) — ไม่งั้นทุกอย่างที่สร้างทับพิสูจน์ไม่ได้
2. **แยกตาราง Δ เป็น 2 คอลัมน์** (อุทกวิทยา vs ปฏิบัติการ) — แก้บั๊ก §2.1
3. **แก้ข้อความ**: "19 จุด มีระดับ+Q+ฝน" → ระบุรายจุดว่ามีอะไร (§2.2 · **ฝนมีจริงที่ 61/62/63/84**) · NY.3 = **ไม่แน่นอน** ไม่ใช่ "หาย" หรือ "เสีย" (§2.3)
4. **ติดป้ายสวิตช์คลอง = หลักฐาน M3** ไม่ใช่ M4 (§2.4) — และขยายจาก 1 จุดเป็นทั้งสาย
5. **กรอง `station_type`** ก่อนดึง thaiwater (§2.5)
6. **ระบุชัดว่าเป้าหมาย 2 ติด rating คลอง** — ใส่ FOI เป็นเงื่อนไขตั้งต้น ไม่ใช่ของแถม
7. **ประเมินงานเป้าหมาย 4 ใหม่** — routing เป็นงานพัฒนา ไม่ใช่ parameter sweep (§2.6)
8. แก้ docstring `fetch_khundan_training.py` ให้ระบุรูปแบบการดึงตรงกับที่ทดสอบ (§4)

แต่ **ยังไม่ควรลงมือสร้างทับ** เพราะ (ก) ยังไม่มี raw data ใน repo (ข) ตาราง Δ มีบั๊กเชิงวิธี (ค) แผนประเมินความพร้อมของ Q/ฝน/วัตถุประสงค์ 2 สูงเกินจริง
แก้ 3 ข้อนี้ก่อน แล้วแผนนี้จะกลายเป็นงานที่มีคุณค่าสูงมาก
