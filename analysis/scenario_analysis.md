# Scenario Analysis: ถ้าบริหารน้ำเขื่อนขุนด่านปราการชล ตาม Upper Rule Curve ตั้งแต่ 30 ส.ค. 2569

**สถานะ**: ฉบับ 1.0 (4 ต.ค. 2569) | **ข้อมูลตั้งต้น**: `dam_khun_dan_daily_2013_2026.csv` (thaiwater.net API, dam_id=32)
**ไฟล์ผลลำดับรายวัน**: `scenario_absorb_peak_sep2026.csv`

> คำเตือนความซื่อตรง: การจำลองนี้เป็น *hindsight แบบ deterministic* — ใช้น้ำเข้า (inflow) ที่เกิดขึ้นจริงทุกวัน ซึ่งในทางปฏิบัติผู้ควบคุมเขื่อนไม่อาจรู้ล่วงหน้าได้ ผลลัพธ์คือขอบเขตบนของผลดีที่ "การทำตาม rule curve อย่างเคร่งครัด" จะให้ ไม่ใช่การพิสูจน์ว่าเหตุการณ์น้ำท่วมจะไม่เกิด

**ปริมาณรวมที่ผลักลงแม่น้ำช่วงหน้าต่างน้ำท่วม 26–29 ก.ย.**: สจ. ~38 ลลบ.ม. เทียบจริง ~55.7 ลลบ.ม. → น้อยลง ~17.6 ลลบ.ม. ในช่วงที่เมืองจมน้ำ โดยย้ายปริมาณนี้ไปก่อนพายุ (ปลาย ส.ค.) และหลังน้ำหน้าเมืองลด (30 ก.ย.เป็นต้นไป)

## 3. การแปลผล — อะไรที่ scenario นี้ *ไม่ได้* บอก

1. **ไม่ป้องกันพีคระดับน้ำที่เมืองได้** — หลักฐาน hydrograph รายชั่วโมง (`event_timeline_sep2026.md`) ชี้ว่า พีค Ny.7 9.23 ม. เกิด 10:00 ของ 27 ก.ย. *ก่อน* ที่เขื่อนจะเปิดสปิลเวย์เต็ม (บ่าย 27 ก.ย.) คลื่นพีคมาจากฝนตกหนักข้ามคืน 26→27 ในลุ่มรับน้ำเบื้องล่างเป็นหลัก → น้ำท่วมขั้นต้น (initial peak) เกิดแม้ไม่มีการปล่อยของเขื่อน
2. **สิ่งที่ลดได้คือ "ความยาว/ความลึกของช่วงน้ำค้าง"** — จริง 27–29 ก.ย. ผลักลง 55.7 ลลบ.ม. ทับซ้อนกับช่วง Ny.7 ≥ 8 ม. ยาว 75 ชม. การลดเหลือ 38 ในหน้าต่างเดียวกัน (และยกไปก่อน/หลัง) ย่อมหดระยะน้ำสูงเฉพาะส่วนที่มาจากเขื่อน — ต้องการ model routing (HEC-RAS) เพื่อบอกตัวเลข "กี่ชั่วโมง กี่ ซม." อย่างเคร่งครัด ซึ่งอยู่นอกขอบเขตข้อมูลปัจจุบัน
3. **จุดตั้งต้นของปัญหา** — สถานการณ์จริงวันที่ 26 ก.ย. น้ำเก็บ 224.3/224.9 เหลือ freeboard 0.6 ลลบ.ม. เท่านั้น → ทางเลือก "ไม่ปล่อยแรง" ถูกตัดขาดตั้งแต่ต้น นี่คือผลสะสมของการปล่อยตามแผนส่งน้ำเกษตร (0.54–1.27) ยาวนาน 36 วันต่อเนื่องขณะอยู่เหนือ URC (30 ส.ค.–4 ต.ค.)

## 4. ข้อจำกัดของการจำลอง

- inflow รายวันมาจากสมดุลมวลน้ำของอ่าง (บวกการระเหย~ตายสมมติ) — ค่า API อาจมี noise วันต่อวัน
- ไม่ได้จำลอง routing ลงแม่น้ำ (travel time เขื่อน→Ny.7 ~10–12 ชม. จากหลักฐาน hydrograph)
- เกณฑ์ URC (ระเบียบ กช.) อาจมีบทยกเว้นกรณีเก็บน้ำเพื่อการใช้สอยฤดูแล้ง — ต้องหาเอกสารระเบียบจริง (งานที่ค้าง)
- cap 8 ลลบ.ม./วันเป็นสมมติฐานของเรา — ไม่ใช่ข้อกำหนดของเขื่อน

## 5. ข้อค้นพบหลัก (สำหรับรายงาน)

**F-SC1**: ถ้าเขื่อนไล่น้ำเก็บลง URC ระหว่าง 30 ส.ค.–1 ก.ย. (ปล่อย ~8 ลลบ.ม./วัน × 3 วัน) แล้วปล่อยปกติตามแผน ณ วันพายุ 26 ก.ย. จะมี freeboard ~25 ลลบ.ม. แทนที่ 0.6 → วันพีค 27 ก.ย. จะต้องระบายจำเป็นเพียง **12.1 ลลบ.ม./วัน (140 ลบ.ม./วิ)** แทนที่ **31.66 (366 ลบ.ม./วิ)** = ต่ำกว่า 62% และต่ำกว่าอัตราจริงของวันที่ 28 ก.ย. ที่ถูกสั่งให้ลดลงเสียอีก

**F-SC2**: การปฏิบัติจริง 1–22 ก.ย. เทียบกับ "ตารางระบายน้ำ ก.ย. 69" ที่โครงการประกาศเอง ตรงกันเป๊ะ (1.209+0.065=1.274 ≈ ค่าจริง 1.27) — แปลว่าเขื่อนทำตามแผนส่งน้ำของตนเอง แต่ **แผนนั้นไม่มีบทบาทการระบายลดระดับแม้น้ำเก็บเกิน URC แล้ว 36 วัน** คำถามเรื่องมาตรฐานจึงอยู่ที่ "แผน/ระเบียบไม่มีกลไกตอบสนองการเกิน URC" ไม่ใช่ "ปฏิบัติผิดแผน"

**F-SC3**: แม้ใน scenario ที่ดีที่สุด วันที่ 27 ก.ย. ยังต้องปล่อย ≥12 ลลบ.ม./วัน และน้ำเก็บยังต้องขึ้นถึง 224.9 — ฝน 18 วัน (1,050–1,420 มม. แถบเขา) ใหญ่เกินกว่าความจุอ่างที่เหลือ สนับสนุนข้อสรุปว่าน้ำท่วม อ.เมือง เป็นเหตุการณ์ฝนเป็นหลัก ซึ่งการบริหารเขื่อนมีบทบาท "ขยายความรุนแรง/ยืดระยะ" ในช่วงท้าย ไม่ใช่ต้นเหตุของพีค
