## 1. API คลังข้อมูลน้ำแห่งชาติ (thaiwater.net) ✅

> คู่มือสถาปัตยกรรม, Endpoint, Gotchas และโค้ดตัวอย่างฉบับสมบูรณ์: [`docs/THAIWATER_API_GUIDE.md`](docs/THAIWATER_API_GUIDE.md)

- Base: `https://api-v3.thaiwater.net/api/v1/thaiwater30/...` — **GET ไม่ต้อง auth**
- วิธีค้นพบ endpoint: แงะ JS bundle ของ `https://www.thaiwater.net/dist/js/app.chunk.js` แล้ว grep ชื่อ path (เว็บเป็น SPA หน้าเว็บเองไม่มีข้อมูล)
- Endpoint ที่ใช้จริง:

## 7. แหล่งที่ติดปัญหาและข้อมูลที่ไม่มีออนไลน์

- haii.or.th (โทรมาตร HAII) — ติดต่อไม่ได้จากเครือข่ายนี้
- onemap.go.th (LiDAR) — ติดต่อไม่ได้; ถ้าได้ = DEM ละเอียดกว่ามาก
- ระเบียบ กช. การระบายน้ำจากเขื่อน — เอกสารภายใน ไม่มีสาธารณะ → FOI
- ตารางบานประตูรายชั่วโมงจาก สช.9 และ ปตร. 2,315 แห่ง — ไม่มีใน API → FOI
- ประวัติการเดินเครื่องสูบน้ำ สนน. กทม. และ ปตร. ปากอ่าว — ไม่มีใน API → FOI
- รูปตัดขวางท้องน้ำจริงใต้น้ำ (Bathymetry) — กรมเจ้าท่า / กช. → ขอทางวิชาการ/FOI

## 9. วงจรชีวิตข้อมูลและการเลื่อนสถานะตัวเลข (Analysis-to-Canonical Lifecycle Protocol)

กระบวนการนำเข้าและยกระดับตัวเลขจากการวิเคราะห์สู่รายงานทางการ ต้องผ่าน 4 ขั้นตอนอย่างเคร่งครัด:

```
[1. การนำเข้าข้อมูลดิบ] ──> [2. การวิเคราะห์เฉพาะเรื่อง] ──> [3. การเลื่อนสู่ตัวเลขทางการ] ──> [4. การสร้างรายงานและทดสอบ]
  data/XX_*/raw/             analysis/goalX_*.py           analysis/*/canonical.json           report/*.html (Builders)
  + manifest.md              + ..._summary.json            (ห้ามเขียนทับด้วยมือ)                 + pytest (MISMATCH = 0)
  + _hashes.txt              + ..._report.md
```

1. **ชั้นที่ 1 — การนำเข้าข้อมูลดิบ (Raw Ingestion)**:
   - บันทึกไฟล์ดิบลงในโฟลเดอร์ `data/<ลำดับ>_<ชื่อ>/raw/`
   - จัดทำเอกสาร `manifest.md` อธิบายที่มา วันเวลา และเงื่อนไขลิขสิทธิ์
   - คำนวณรหัสตรวจสอบ SHA-256 ลงในไฟล์ `_hashes.txt` (ตรวจผ่าน `verify_data_integrity.py`)
2. **ชั้นที่ 2 — การวิเคราะห์เฉพาะเรื่อง (Specialized Analysis)**:
   - สร้างสคริปต์วิเคราะห์ใน `analysis/` โดยขึ้นต้นด้วยคำนำหน้าที่ระบุเป้าหมาย (`goal2_`, `goal6_`, `goal7_`, `common_`)
   - บันทึกผลลัพธ์เป็นไฟล์ JSON สรุปผล (`..._summary.json`) และรายงานสรุป (`..._report.md`)
3. **ชั้นที่ 3 — การเลื่อนสู่ตัวเลขทางการ (Canonical Promotion)**:
   - เมื่อตัวเลขผ่านการพิสูจน์แล้วและพร้อมใช้อ้างอิงข้ามรายงาน ให้นำตัวเลขเข้าสู่ `canonical.json` ผ่านสคริปต์ผู้สร้างทางการ (เช่น `build_canonical_numbers.py` หรือ `goal6_canonical.py`)
   - **ห้ามแก้ไข `canonical.json` ด้วยมือโดยเด็ดขาด** และหากมีค่าเก่าที่ถูกแทนที่ ให้บันทึกลงในบัญชีรายการปลดระวาง (retired ledger) พร้อมระบุเหตุผล
4. **ชั้นที่ 4 — การสร้างรายงานและการทดสอบ (Report Integration & QA)**:
   - ตัวสร้างรายงาน (Builders) ดึงตัวเลขจาก `canonical.json` ไปเรนเดอร์ลงในบทความและตาราง
   - รันชุดทดสอบความสอดคล้อง (`test_goal6_consistency.py`, `test_standards_integrity.py`) เพื่อยืนยันว่าไม่มีตัวเลขลอยหรือตัวเลขขัดแย้ง

## 10. การดูแลสุขอนามัยของโค้ดและข้อมูล (Code & Data Hygiene)

1. **การจัดการไฟล์ชั่วคราว (Scratch Files)**:
   - ไฟล์ทดสอบ สคริปต์สำรวจ API หรือผลการทดลองชั่วคราว ต้องเก็บในโฟลเดอร์ `scratch/` หรือตั้งชื่อขึ้นต้นด้วย `_tmp_` เสมอ
   - ห้าม commit ไฟล์ชั่วคราวเข้าสู่คลังโค้ด
2. **การคงสภาพแฮช (Data Immutability)**:
   - ข้อมูลดิบใน `data/` ถือเป็นพยานหลักฐานทางนิติวิทยาศาสตร์อุทกวิทยา ห้ามแก้ไขไฟล์เดิมหลังบันทึกแฮชแล้ว หากมีข้อมูลชุดใหม่ให้สร้างโฟลเดอร์หรือไฟล์ใหม่พร้อมบันทึกประวัติการสืบค้น
3. **การลงทะเบียนในสารบัญระบบ**:
   - สคริปต์และชุดข้อมูลใหม่ทุกชุดต้องลงทะเบียนใน `catalog.py` และ `docs/PROJECT_MAP.md` ทันที และต้องผ่านการตรวจสอบด้วย `python catalog.py check`
