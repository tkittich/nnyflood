# วิธีการและมาตรฐานการทำงานของโปรเจค (METHODS)

> หลักการสูงสุด: **ทุกข้อสรุปต้องตรวจสอบย้อนกลับถึงหลักฐานได้ และโปรเจคต้องเป็นกลางทางวิชาการ**

## 1. มาตรฐานหลักฐาน (Evidence Protocol) — บังคับใช้กับทุกการเก็บข้อมูล

1. **ต้นฉบับก่อนเสมอ**: เก็บไฟล์ดิบตามสภาพที่ได้รับ (JSON/HTML/ภาพ/PDF) ห้ามเก็บเฉพาะค่าที่คัดลอก
2. **ลงทะเบียนทุกไฟล์** ใน `manifest.md` ของโฟลเดอร์นั้น: ชื่อไฟล์ · ได้มาเมื่อ (วัน-เวลา) · URL/พารามิเตอร์ · วิธีดึง
3. **SHA-256** ของไฟล์สำคัญ (ภาพหลักฐาน, CSV สังเคราะห์) บันทึกใน manifest — คำนวณด้วย `sha256sum`
4. **Screenshot** ทุกครั้งที่อ้างหน้าเว็บ/โพสต์โซเชียล (กันต้นฉบูลถูกลบ/แก้) — เก็บคู่กับ raw
5. **Wayback Machine** (web.archive.org/save) สำหรับข่าว/แถลงการณ์สาธารณะที่สำคัญ — ชั้นหลักฐานที่สอง
6. **OCR/โมเดลวิเคราะห์ภาพ = ข้อมูลถอดความ** กำกับ `[OCR?]` ทุกจุดที่ไม่แน่ใจ และต้องมีมนุษย์ตรวจกับภาพก่อนขึ้นรายงาน

## 3. วิธีดึงข้อมูล (เพื่อทำซ้ำได้)

- API คลังข้อมูลน้ำแห่งชาติ: HTTP GET ตรง (curl/urllib) ไม่ต้อง auth — รายละเอียด endpoint/พารามิเตอร์/ข้อจำกัด ดู `DATA_SOURCES.md`
- การพิสูจน์วิธีเรียก API ย้อนหลัง: อ่านจาก JS bundle ของเว็บ (`app.chunk.js`) — วิธีนี้ใช้ต่อได้กับ endpoint ที่ยังไม่รู้พารามิเตอร์
- ข้อมูลที่ต้องเก็บซ้ำในอนาคต (เช่น รายวันถัดไป): ใช้สคริปต์ต้นแบบใน analysis/ — ถ้าไม่มีให้เขียนใหม่ตาม DATA_SOURCES ได้เลย

## 4. หลักความเป็นกลางของการวิเคราะห์

1. ห้ามตั้งข้อสรุปล่วงหน้า — ทุกข้อสรุปต้องผ่าน "การพยายามหักล้าง" เป็นอย่างน้อย 1 ครั้ง
2. แยก **ข้อเท็จจริงจากข้อมูล** (fact) ออกจาก **การตีความ** (interpretation) ออกจาก **การประเมินตามมาตรฐาน** (assessment) ชัดเจนในรายงาน
3. การประเมิน "ตามมาตรฐานหรือไม่" ต้องระบุเกณฑ์ก่อนเสมอ (URC/LRC, ระเบียบ กช., แผนลุ่มบางปะกง) และระบุว่าเกณฑ์นั้นบังคับจริงหรือเป็นแนวปฏิบัติ
4. ข้อมูลฝนเป็นตัวแปรกวน (confounder) หลักของการประเมินผลการปล่อยน้ำ — ต้องควบคุมด้วยการเลือกช่วงเวลา/สถานีเปรียบเทียบ (ดู ANALYSIS_PLAN)
5. อ้างอิงทุกตัวเลขในรายงาน: (แหล่ง, วันที่ข้อมูล, วันที่ดึง) — รูปแบบเดียวกันทั้งฉบับ

## 5. ข้อควรระวังเชิงข้อมูลที่รู้แล้ว (Data Caveats)

- ค่ารายวันของเขื่อน "วันที่ D" จาก API คือตัวเลขสรุปของวัน — ช่วงเวลาตัดรายงานอาจไม่ตรงกับรายงาน 08:00 น. ของเพจเขื่อน 100% (พบต่างกันเล็กน้อยในบางวัน)
- ระดับแม่น้ำรายสถานีอ้างมาตรฐานเฉพาะสถานี (ไม่ใช่ ม.รทก.) — เทียบข้ามสถานีโดยตรงไม่ได้ ให้เทียบ "การเปลี่ยนแปลงจากฐานของสถานีตัวเอง"
- API ฝนมีเฉพาะปีปัจจุบัน + null อาจแปลว่า "ไม่มีฝน" หรือ "ไม่มีข้อมูล"
- `dam_spilled=0` ≠ ไม่มีการระบายที่สปิลเวย์ — การเปิดประตูสปิลเวย์นับเป็น "ปล่อย" (released) ไม่ใช่ "ล้น"

## กรณีศึกษาตรวจสอบไขว้: กราฟโครงการ (566658.jpg) สะสม Inflow/Outflow

**เทียบเท่าสะสมปี 69** จากข้อมูลรายวัน API (ถึง 4 ต.ค.): **inflow 340.884 / released 302.441 ลลบ.ม.**

| ที่มา (ณ วัน) | สะสม Inflow | สะสม Released |
|---|---|---|
| API รายวัน (4 ต.ค.) | 340.884 | 302.441 |
| 566658.jpg OCR (4 ต.ค.) | 340.288 ✓ ใกล้เคียง | **339.872 ✘ ห่าง +37** |
| อินโฟฯ 3 ต.ค. (S__8691761) | 331.108 (Δ ~6 จาก API) | 307.084 (Δ ~8 จาก API) |

**ข้อสรุป**:
1. **ตัวเลข 339.872 เป็นตัวเลขจริงบนกราฟโครงการ** (อ่านซ้ำอย่างละเอียดทีละหลัก ยืนยันทั้งในกล่องคำอธิบายและป้ายเส้นกราฟ) — ไม่ใช่ความผิดพลาดการอ่าน
2. แต่เมื่อเทียบสะสมรายเดือนกับผลรวม API: กราฟโครงการให้ค่าสะสม Outflow สูงกว่า API อย่างสม่ำเสมอ ~+30–37 ลลบ.ม. ทุกเดือน (ก.ค. 205.7 vs 173.4 / ส.ค. 211.3 vs 181.4 / ก.ย. 285.0→282.43 ใกล้กัน / 4 ต.ค. 339.9 vs 302.4) ขณะที่ Inflow สะสมต่างกันเพียง ~+7 → **กราฟนับส่วน Outflow เพิ่ม ~37 ลลบ.ม. ที่ API "released" ไม่ได้นับ** (น่าจะส่วนเบี่ยงเบนน้ำ/ท่อส่งน้ำเข้าระบบอื่น เช่น โครงการเขื่อนทดน้ำ นครนายก — ต้องสอบถามนิยามกับโครงการจึงปิดได้)
3. **Mass balance สนับสนุนชุด API**: S(1 ม.ค.)=188.54 → S(4 ต.ค.)=213.18 (ΔS=+24.6); Σin−Σout(API)=+38.4; ส่วนต่าง −13.8 ≈ การระเหย+ซึม 9 เดือน (สมเหตุผล ~1.5 ลลบ.ม./เดือน) — ขณะที่ค่าคู่ของกราฟ (in 340.3/out 339.9, net −0.4) ขัดกับ ΔS=+24.6 ของน้ำเก็บตัวเอง
4. **กฎการใช้งาน**: อ้างสะสมปี 69 ให้ใช้ชุด API (302.441/340.884 ณ 4 ต.ค.) เป็นหลัก; ตัวเลขกราฟโครงการใช้ได้เมื่ออ้าง "ตามการนับของโครงการ" พร้อมหมายเหตุฐานต่าง
5. ข้อสังเกตเพิ่ม: API บันทึก inflow = 0.00 ทุกวัน ม.ค.–เม.ย. 69 (ฤดูแล้ง) — ผ่าน mass balance (การสูญเสียของช่วงนั้นอธิบายด้วยการปล่อย 161.5 + ระเหย/ซึม ~2–3 ได้พอดี)

**datum จุดวัดระดับน้ำ**: ทะเบียนสถานี thaiwater (station_all.json) ไม่มีฟิลด์ datum/benchmark → Ny.7/Ny.1B ยังเป็นหน่วยมาตรประจำสถานี (ไม่ใช่ ม.รทก.) — ต้องขอเอกสารสถานีจาก สช.9/HII


## 6. การประมวลผล Sentinel-1 เอง + การสอบเทียบกับ GISTDA

**Pipeline** (สคริปต์ `analysis/s1_process.py`, `s1_masks.py`, `s1_change_detect.py` — ทำซ้ำได้):
1. ต้นฉบับ GRDH COG 7 ฉากจาก CDSE (ผู้ใช้ดาวน์โหลดเองด้วยบัญชีฟรี — ผู้ช่วยไม่แตะข้อมูลส่วนตัว) ทะเบียน+SHA-256 ใน `data/13_sentinel1_copernicus/manifest.md`
2. Geocode: GCP 210 จุด/ฉาก (annotation XML) → forward cubic spline + Newton inversion (ค่าเริ่มจาก GCP ใกล้สุด กันหลุดโดเมน) — **roundtrip 0.00 px ทุกฉาก** · ไม่มี terrain correction (พื้นที่เป้าหมายคือที่ราบ)
3. Calibrate: σ₀ = DN²/A² จาก sigmaNought LUT · speckle filter 5×5 · กริด WGS84 30 ม. ทั้งจังหวัด (ขอบเขต OSM province relation 1908787)
4. Change detection คู่วงโคจรเดียวกัน (12 วัน): น้ำสูงสุด 27 ก.ย. 18:28 vs 15 ก.ย. 18:28 · สอบเทียบ 2 ต.ค. vs 19 ก.ย.
5. กฎน้ำท่วม: ΔVH≤−1 dB & ΔVV≤−2 dB & VHหลัง≤−18 dB + opening 3×3 — **ตั้งค่าโดย maximize F1 กับผล GISTDA บนฉาก 2 ต.ค. pass เดียวกัน**
