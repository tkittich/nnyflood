# ข้อตกลงการทำรายงาน (Report Conventions)

> สถานะ: สร้าง 16 ต.ค. 69 จากบทเรียนรายงาน 1–8 · **กติกาบังคับระดับ "ละเมิดแล้วเสียหลักฐาน/ตัวเลข" อยู่ใน `AGENTS.md`** —
> ไฟล์นี้คือ "วิธีทำงานให้เป็นระบบ" (โครงสร้าง · เอ็นจิน · ธีม · กราฟ · แผนที่ · การอ่านง่าย) ที่ทำให้แก้/ย้าย/เรียงใหม่ได้โดยไม่พัง
> ใช้กับรายงานใหม่ทุกฉบับ · รายงาน 1–6 ย้ายเข้าระบบนี้เมื่อต้องแก้ครั้งใหญ่ครั้งถัดไป (ไม่รื้อพร้อมกัน)

## 1. หลักใหญ่ 5 ข้อ

1. **ตัวเลขมาจากแหล่งเดียว** — canonical (`analysis/<goal>/canonical.json`) → builder เรนเดอร์ · ห้ามพิมพ์เลข metric เป็น literal
2. **ข้อความที่อ้างเลขข้อ ต้องอ้างด้วยรหัส ไม่ใช่เลข** — ย้าย/รวม/เรียงหัวข้อแล้วเลขตามเอง (§2)
3. **ตารางที่อยู่สองฉบับเขียนที่เดียว** — `report/goal7_blocks.py` (§3)
4. **ตัวตรวจอยู่นอกลูปสร้าง** — เทสต์ตรวจหลังสร้างเสร็จ ไม่ฝังใน builder (AGENTS.md)
5. **เอกสารสถานะต้องตรงรายงาน** — จำนวนถาม–ตอบ/เลขใน HANDOFF มีเทสต์จับ (`test_handoff_question_count_current`)

## 2. เอ็นจินรายงาน (`report/goal7_engine.py`)

| สิ่งที่ต้องการ | วิธี |
|---|---|
| หัวข้อ/คำถามใหม่ | ให้ **key** คงที่ (อังกฤษสั้น เช่น `bank`, `tide`) · ห้ามเปลี่ยน key หลังมีคนอ้าง |
| เรียงลำดับ/จัดหมวดใหม่ | แก้ `CATS` ใน builder ที่เดียว — เลขถาม/เลขข้อ/สารบัญ/คำนำหมวดเปลี่ยนตามอัตโนมัติ |
| รวมคำถามสองข้อ | ใส่ใน `MERGED = {ข้อที่ถูกรวม: ข้อที่รับ}` — โทเคนที่ชี้ข้อที่ถูกรวมจะชี้ข้อที่รับเอง |
| อ้างข้อในข้อความ | `⟦key⟧` → "ถาม 7" / "ข้อ 3.12" · หลายข้อ `⟦a,b⟧` → "ถาม 3, 7" |
| อ้างข้ามฉบับ | `⟦ว:key⟧` (ไปฉบับวิชาการ) · `⟦ป:key⟧` (ไปฉบับประชาชน) → "ฉบับวิชาการ ข้อ 3.12" |
| คำถามสำคัญ | ใส่ key ใน `OPEN` — เปิดไว้ตั้งต้น ที่เหลือพับ (`<details class='qd'>`) |
| key พิมพ์ผิด | **สร้างรายงานล้ม** (ไม่ปล่อยเลขผิดเงียบ ๆ) |

- สร้างทั้งสองฉบับ: `python report/goal7_build_all.py` (วนจนผังหัวข้อนิ่ง — โทเคนข้ามฉบับอ่านผังของอีกฉบับจาก `analysis/goal7/outline_*.json`)
- เทสต์: `test_builders_have_no_hardcoded_numbering_refs` (ห้ามพิมพ์ "ถาม N"/"ข้อ 3.x" ตรง ๆ) · `test_no_unresolved_reference_tokens` ·
  `test_outlines_match_reports` · `test_public_questions_collapsible_and_numbered`
- ข้อความภายใน caption/ตารางก็ใช้โทเคนได้ (ถูกแปลงที่ขั้น `resolve()` ก่อนส่งเข้า `page()`)
- เอกสารนอกรายงาน (HANDOFF, GOAL7_PLAN) อ้าง "ถาม N" ได้เป็นประวัติ — ใส่วันที่กำกับ ไม่ถือเป็นเลขปัจจุบัน

## 3. ชิ้นส่วนร่วม (`report/goal7_blocks.py`)

- ตาราง/ภาพที่ปรากฏทั้งฉบับประชาชนและวิชาการ = ฟังก์ชันใน `goal7_blocks.py` (`tbl_*`) · ต่างกันได้เฉพาะ **caption** และพารามิเตอร์แสดง/ซ่อนคอลัมน์
- ภาพ (กราฟ/แผนที่) ร่วม = `fig_*` ใน `goal7_common.py` (ผลิต PNG ใน `report/assets/` ชื่อคงที่)
- เทสต์ `test_shared_tables_not_duplicated_across_builders` จับหัวตารางซ้ำสอง builder
- ข้อความเล่าเรื่อง (ถาม–ตอบ) เป็นของแต่ละฉบับ — ฉบับวิชาการไม่ต้องเล่าซ้ำ ให้ชี้ไปด้วยโทเคน

## 4. โครงรายงาน (ต่อยอด AGENTS.md "รายงานทุกฉบับเน้นคนทั่วไปอ่านเข้าใจง่ายที่สุด")

1. สรุปสั้น (อ่าน 2 นาที) · 2. บริบทผู้อ่านใหม่ + "อ่านจบในตัวเอง" · 3. "วิธีอ่านรายงานนี้" (หมวดและช่วงคำถาม)
4. เนื้อหา — **หมวดเรียงจากเรื่องที่ผู้อ่านสนใจมากที่สุดไปรายละเอียด** (ไม่เรียงตามลำดับวิจัย) · 5. เสียงจากท้องถิ่น/ข้อห่วงกังวล
6. สิ่งที่ยังไม่รู้ + สิ่งที่ควรขอ · 7. ข้อมูลอ้างอิง (ตารางละเอียด) · 8. ภาคผนวกแหล่งที่มา
- ฉบับประชาชน: ถาม–ตอบพับได้ · **เปิดไว้ 3–12 ข้อสำคัญ (ไม่เกินครึ่งของข้อทั้งหมด)** · ชื่อคำถามเป็นคำถามที่คนถามจริง · แต่ละข้อแยก **ข้อเท็จจริง / การตีความ / การประเมิน**
- ฉบับวิชาการ: ข้อมูลและวิธี → ทะเบียนข้อเท็จจริง → ผล → อภิปราย → ข้อจำกัด · ทุกข้อมีชั้นหลักฐาน (A/B/C)
- รวมข้อซ้ำก่อนเพิ่มข้อใหม่: ถ้าสองคำถามตอบด้วยตัวเลขชุดเดียวกัน ให้รวม (เช่น "ลดคันให้เท่าพื้น" + "ขุดลึก")

## 5. ธีมและสี

- ใช้ `COLOR_TOKENS` ใน `report/goal6_reportlib.py` (พื้น+ตัวอักษรเป็นคู่) — ห้ามเลือกสีใหม่ใน builder
- WCAG: ตัวอักษร ≥ 4.5 · แท่ง/เส้น/พื้นที่ข้อมูล ≥ 3.0 · **ตรวจด้วยการคำนวณจากไฟล์จริงหลังแก้** (ไม่ใช่ตา)
- กราฟ: `INK #1c2b33` · `BLUE #1d6fb8` · `ORANGE #a14a00` · `GREY #5a6b7b` · เสริม `TEAL #0b6f6a` `PURPLE #7a3b8f` (ทุกสี ≥ 3.0 บนขาว)
- ห้ามอาศัยสีอย่างเดียวแยกข้อมูล — เส้น/แท่งสำคัญต้องมีป้าย/ลายเส้น (ประ/ทึบ) กำกับ (ผู้อ่านตาบอดสี/พิมพ์ขาวดำ)
- ปุ่ม/กล่องพับ: พื้นขาว ขอบ `#b9c6d2` ตัวหัวข้อ `#1c2b33` (ค่าอยู่ใน `COLLAPSE_CSS`)

## 6. กราฟ

- ภาษาไทยทั้งหมด · `plt.rcParams["font.family"] = ["Leelawadee UI", "Tahoma"]` · ขนาด 7.4–7.8 นิ้ว กว้าง · dpi 130 · ไฟล์ `report/assets/<goal>_<ชื่อ>.png`
- **หนึ่งกราฟ หนึ่งข้อความ** — ชื่อกราฟบอกข้อสรุป ("ที่ปลายคลองน้ำทะเลสูงกว่าพื้นดินเดิม 1–2 ม.") ไม่ใช่แค่ชนิดข้อมูล
- ป้ายค่าบนแท่ง/เส้นที่สำคัญ · แกนมีหน่วย · เส้นอ้างอิง (ระดับกำกับ/ค่าปกติ/ค่าสูงสุด) ต้องมีป้ายบนกราฟ
- ภาพตัด/แผนผังที่ **สัดส่วนจริง** ใช้ `ax.set_aspect("equal")` และบอกในชื่อ · ถ้าขยายแกนตั้ง ต้องบอกว่าขยาย
- caption ใต้ภาพบอก: อะไร · แหล่ง/วิธี · ข้อจำกัด (ค่าคำนวณเอง/อ่านจากรูป ±)

## 7. แผนที่

- ใช้ฐานเดียวกัน `draw_basemap()` (`goal7_common.py`) — สีพื้น = ความสูง · ถนนสายหลัก · แม่น้ำลำคลอง
- ทุกแผนที่ต้องมี (ที่ยังไม่ครบในรายงานเก่า ให้ทำเมื่อแก้ครั้งถัดไป): หมุดกิโลเมตร/มาตราส่วนหรือระยะ · คำอธิบายสี · ทิศเหนือ (หรือระบุว่าเหนืออยู่ด้านบน) · แหล่งข้อมูลชั้นข้อมูล
- ข้อมูลไม่เป็นทางการ (เช่น แนวคลองจากแผนที่ผู้ใช้) ต้องบอกบน caption ทุกครั้งว่า "ไม่ใช่แนวทางการ"
- ข้อมูลความสูง/ผังน้ำ: ระบุความคลาดเคลื่อน (DEM ±2–4 ม.) เสมอ

## 8. ภาษาและการอ่านง่าย

- ภาษาไทยล้วนตามบัญชี `BANNED_TERMS`/`SOFT_RULES` (reportlib) และ `PLAIN_TH` (goal7_common) · ศัพท์จำเป็นให้อธิบายตอนใช้ครั้งแรก
- ประโยคยาวเกิน ~3 บรรทัดให้แตก · หนึ่งย่อหน้าหนึ่งประเด็น · ตัวเลขสำคัญตัวหนา + หน่วย + ที่มา
- ใช้ **ตารางแทนย่อหน้า** เมื่อเทียบหลายทางเลือก (ตาราง "ทางเลือก × ขนาด × ที่ดิน × ไฟ × ผลต่อทะเล")
- ย่อหน้าวิเคราะห์ใช้ป้าย **ข้อเท็จจริง / การตีความ / การประเมิน** · กรณีของผู้จัดทำใช้ป้าย **"ข้อเสนอของผู้จัดทำ — ไม่ใช่ข้อมูลทางการ"**
- กรอบวิจารณ์ = ระบบ/ระเบียบ/วิธีการ ไม่ใช่บุคคล (หมิ่นประมาท/PDPA — `docs/LEGAL_REVIEW.md`)
- ข้อสรุปเชิงตัวเลขจากสมมติฐาน ต้องบอกสมมติฐานติดกับตัวเลข (ราคา/จำนวนวัน/สัมประสิทธิ์) และเก็บใน canonical → `assumptions`

## 9. กรณีคำนวณของผู้จัดทำ (ชั้น C)

- อยู่ใน `canonical.json` ฟิลด์ของตัวเอง (เช่น `new_cases`) · ทุกค่ามี `assumptions`/`src` · เป็น "คัดกรองลำดับขนาด" ไม่ใช่แบบ
- เขียนคำนวณไว้ในฟังก์ชันของ `analysis/<goal>_analysis.py` (ไม่คำนวณใน builder) · ล็อกค่าสำคัญด้วย regression test
- ต้องมีเทียบ "ตามแบบ" กับ "กรณีใหม่" ในหน่วยเดียวกัน (ตาราง 2–3 คอลัมน์)
- ข้ออ้างจากภายนอก (สถิติโลก ราคาตลาด) ต้องมีแหล่ง+วันที่ค้น หรือติดป้ายว่า "ยังไม่ได้ตรวจ" และลงทะเบียนช่องว่าง

## 10. ทะเบียนช่องว่างและเอกสารสถานะ

- ประโยค "ไม่พบ/ยังไม่รู้" ทุกประโยคมี `# gap: <id>` ใน builder (AGENTS.md) · ปิดช่องว่าง = เปลี่ยน status แล้วเทสต์ชี้บรรทัดที่ต้องแก้
- ปิดงานรอบ: (1) `python analysis/<goal>_analysis.py` (2) `python report/goal7_build_all.py` (3) `pytest` (4) HANDOFF + แผน (§สถานะ) (5) commit
- commit ข้อความไทย: เป้าหมาย N: <ทำอะไร> — ผู้ใช้ push เอง (agent ไม่ push)

## 11. ควรมีเอ็นจินที่ดีกว่านี้ไหม — ข้อสรุป (16 ต.ค. 69)

- **ตอนนี้พอ:** เอ็นจินเบา (ทะเบียน key + โทเคน + บล็อกร่วม) แก้ปัญหาที่เกิดจริง 3 อย่าง: เลขข้อเลื่อน · ตารางซ้ำสองฉบับ · เอกสารสถานะล้าสมัย
- **ไม่ควรเพิ่ม** เครื่องมือหนัก (Quarto/Jinja/Sphinx) จนกว่าจะมี ≥ 3 ฉบับที่ใช้โครงเดียวกัน — ต้นทุนย้าย + ฟอนต์ไทยในกราฟ + ตัวตรวจภาษาที่มีอยู่
- **ขั้นถัดไปที่คุ้ม (เมื่อมีรายงานใหม่):** ย้าย `Outline`/`details`/`COLLAPSE_*` จาก `goal7_engine.py` ไป `report/` ระดับกลาง (ไม่ผูกเป้าหมาย 7) แล้วให้รายงาน 3/4/5 ใช้ตอนต้องแก้ครั้งใหญ่
- **สิ่งที่ยังเป็นความเสี่ยง:** (1) builder ยาว 800–900 บรรทัด ข้อความเล่าเรื่องปนโค้ด — ควรแยกข้อความเป็นไฟล์ข้อมูลเมื่อมีผู้เขียนหลายคน
  (2) จัดกลุ่มคำถามผ่านตัวแปร `G`/marker `S.group()` ยังเปราะต่อการแก้ไขมือ — ถ้าจะทำต่อ ให้เปลี่ยนเป็น decorator/ฟังก์ชันต่อคำถาม
