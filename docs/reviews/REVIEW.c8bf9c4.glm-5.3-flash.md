## 3. Deep-Dive Technical Findings

### [F-01] Maeklong "sensitive to reference" label is driven by a peak-pass switch
- **Location**: `analysis/goal6/s1_ref_sensitivity_maeklong.json`; Report 3 (`report/ระลอกปลายกย2569.html`), sentence "ความไวต่อวันของฉากอ้างอิง (ลุ่มแม่กลอง … ค่าสูงสุดของลุ่มเปลี่ยนจาก 380 เป็น 420 ตร.กม. (+10.4%)".
- **Empirical evidence** (recomputed from `passes`, role `event_or_after`):

  | orbit | date | primary km² | alt-ref km² | change | coverage |
  |---|---|---|---|---|---|
  | 31 | 1 Oct | 380.3 | 395.0 | +3.9% | 0.603 |
  | 39 | 2 Oct | 87.5 | 27.6 | −68.5% | 0.83 |
  | 104 | 24 Sep | 15.2 | 16.2 | +6.6% | 0.611 |
  | 141 | 27 Sep | 332.2 | **419.9** | +26.4% | 0.391 |

  `peak_primary_km2` = 380.3 (orbit 31) but `peak_alt_ref_km2` = 419.9 (orbit 141). The summary's +10.4% — and the basin's "ไวต่อฉากอ้างอิง" label (the only one of six basins labelled) — is the ratio of peaks from **different passes**. For Pasak, Thachin, Ping–CP and Bangkok-lower the same pass sets both peaks (verified per JSON).
- **Critique**: the prereg defines the label as a table label, so nothing mis-states a definition; and the report's closing line ("ให้อ่านค่าสูงสุดเป็นช่วงระหว่างค่าฉากหลักกับค่าฉากทางเลือก") points in the right direction. But a reader cannot see *why* Maeklong alone is labelled: it is because a lower-coverage pass (0.391) takes over as the maximum, not because the same measurement moved 10%. That distinction changes how the label should be read.
- **Proposed solution**: print the orbit and date of each peak (data already in the JSON), e.g. "ค่าสูงสุดฉากหลักมาจากวงโคจร 31 ส่วนค่าสูงสุดฉากทางเลือกมาจากวงโคจร 141". Wording only; no recomputation; inside the prereg's descriptive-only boundary.

### [F-02] Two paths to the 2011 dam benchmark, and a window count named like a year count
- **Location**: `report/goal6_build_report4_draft.py:24-27` (`dams = … dam_history_all.json … days54 = next(r["days_over_urc"] …)`); `analysis/goal6_canonical.py:170` (`"days_over_2554": (r["y2554"] or {}).get("days_over_urc_window")`); `analysis/goal6/canonical.json`.

### [F-04] Literal-gate year band exempts every unit (reproduced)
- **Location**: `tools/number_inventory.py`, `builder_literals` filter: `if digits >= 3 and unit not in ("year",) and not (2400 <= val <= 2600)`.

## 7. Overall System Suggestions & Consistency Recommendations

1. **Make canonical coverage declarative (closes the F-02/F-03/F-07 class).** Add `render_status` to every top-level key of both canonicals and enforce with a test: builder-read XOR `internal_only(reason)` XOR `superseded_by(key)`. This is the inverse of the round-8 empty-table test, and it converts the most expensive part of each audit round (forensic key tracing) into a gate. The `retired.json` refactor (round 8, GL F-06) proves the pattern works here.
2. **One number, one path (F-02).** Where a canonical key duplicates a builder-side derivation, delete one path. The test should assert the *report text* against the canonical, not the canonical against itself.
3. **Field names carry windows; definitions are not optional (F-02).** The `days_over_urc / …_sep_oct / …_aug_sep` naming family plus `definitions` entries is the house style — apply it to `dam_inflow.days_over_2554/2569`.
4. **Fix the gate's year band before the next allowlist review (F-04)**; treat any allowlist diff that is not deletion-only as an explicit, logged exception (the R8-01 precedent).
5. **Docs are part of the ledger (F-05).** A weekly (or pre-release) retired-value scan over root + docs `*.md` with a negative-example allowlist would have caught the prompt's stale range before three more reviewers copied it.
6. **Process**: the parallel-session collision (§0) and the auto-restamping of `verification.json` interact badly during review rounds — three sessions are now writing `docs/reviews/` while each `verify_all` run rewrites a tracked file. Cheapest mitigation: reviewers run the four gates individually (`pytest`, integrity, catalog, doctor) instead of `verify_all`, and let the owner's post-triage rebuild restamp; or `write_verification.py` gains a `--no-write` mode that reviewers are told to use.
